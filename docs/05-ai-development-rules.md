# AI Development Rules

## Правила работы ИИ-агента

Проект: Система экранного OCR-перевода игровых субтитров и текста для Windows 11

Версия документа: 1.1 (обновлено)

------------------------------------------------------------------------

# 1. Назначение документа

Определение правил работы ИИ-агента для сохранения архитектурной целостности, предотвращения неконтролируемого рефакторинга, уменьшения техдолга.

------------------------------------------------------------------------

# 2. Главный принцип

Агент обязан сначала завершать текущий этап разработки, затем переходить к следующему. Запрещено самостоятельно изменять Roadmap.

------------------------------------------------------------------------

# 3. Приоритет документов

1. Техническое задание (обновлённое)
2. Архитектурный документ (обновлённый)
3. Технические риски и спорные решения
4. Roadmap
5. Данный документ

------------------------------------------------------------------------

# 4. Что агент обязан делать перед изменением кода

Определить текущий этап Roadmap, проверить зависимые модули, существующие интерфейсы, требования ТЗ, ограничения архитектуры.

------------------------------------------------------------------------

# 5. Что агенту запрещено менять без разрешения

Язык: C#. UI: WPF (не WinUI 3). Архитектура: MVVM + Clean Architecture. Хранилище профилей: JSON. Хранилище ключей: Windows Credential Manager. База данных: SQLite. Захват экрана: Windows Graphics Capture. Многодвижковая архитектура OCR. Многопровайдерная архитектура переводчиков. Структура OCR-зон. Система слоев Overlay. Запрет на DLL Injection, Memory Reading, Memory Injection. Использование Tesseract для вертикального текста. Маскирование без blur (solid/darken).

------------------------------------------------------------------------

# 6. Запрет на преждевременную оптимизацию

До завершения MVP запрещается массовый рефакторинг ради производительности. Допускается исправление явных узких мест.

------------------------------------------------------------------------

# 7. Правило минимальных изменений

Каждая задача решается минимальным объёмом изменений. Запрещено переписывать модуль полностью, если можно расширить интерфейс.

------------------------------------------------------------------------

# 8. Правило обратной совместимости

Изменения должны сохранять работоспособность существующих профилей (с миграцией версий).

------------------------------------------------------------------------

# 9. Правило интерфейсов

Новые модули подключаются через интерфейсы, используется Dependency Injection.

------------------------------------------------------------------------

# 10. Правило OCR

Каждый OCR-движок реализует `IOcrEngine`. Код не должен зависеть от конкретного OCR. Для вертикального текста обязательно использовать Tesseract.

------------------------------------------------------------------------

# 11. Правило переводчиков

Каждый переводчик реализует `ITranslatorProvider`. Автоматическое переключение между провайдерами не требуется.

------------------------------------------------------------------------

# 12. Правило профилей

Добавление новых параметров через версионирование профиля (`schemaVersion`). Каждый профиль содержит `schemaVersion`.

------------------------------------------------------------------------

# 13. Правило секретов

API-ключи никогда не сохраняются в JSON, SQLite, логах, отладочных файлах. При выводе маскировать (например, `****ABCD`).

------------------------------------------------------------------------

# 14. Правило логирования

Логировать ошибки и предупреждения. Запрещено логировать пароли, API-ключи, секреты.

------------------------------------------------------------------------

# 15. Правило исключений

Запрещено пустое `catch { }`. Каждое исключение обрабатывается или логируется. Пользователю показываются только ошибки сети и недоступности переводчика.

------------------------------------------------------------------------

# 16. Правило асинхронности

Сетевые операции, OCR, перевод, захват экрана – асинхронны, вне UI-потока.

------------------------------------------------------------------------

# 17. Правило производительности

Перед оптимизацией измерить производительность. Целевые показатели: OCR ≤200 мс, средний CPU ≤25%, память ≤500 МБ.

------------------------------------------------------------------------

# 18. Правило Overlay

Overlay – независимый модуль. Не встраивать в OCR или переводчики.

------------------------------------------------------------------------

# 19. Правило многозонности

Все новые функции обязаны учитывать множество OCR-зон.

------------------------------------------------------------------------

# 20. Правило координат

Все координаты поддерживают абсолютный и относительный режимы.

------------------------------------------------------------------------

# 21. Правило кэша

Перед отправкой на перевод проверять кэш (TTL 30 дней). Запрещено обращаться к API без проверки кэша.

------------------------------------------------------------------------

# 22. Правило тестирования

Каждый модуль должен иметь минимальные тесты (успешный и ошибочный сценарий). Для ProfileValidator, CoordinateTransformer, CacheManager покрытие юнит-тестами не менее 80%.

------------------------------------------------------------------------

# 23. Правило Definition of Done

Задача завершена, если код компилируется, запускается, нет критических ошибок, обновлена документация, выполнены проверки этапа Roadmap.

------------------------------------------------------------------------

# 24. Что агент обязан выдавать после каждой задачи

Список изменённых файлов, краткое описание, возможные риски, следующий шаг, статус Roadmap.

------------------------------------------------------------------------

# 25. Запрещённые действия

Удаление рабочих модулей, переписывание архитектуры без запроса, изменение формата профилей без миграции, отключение логирования, отключение обработки ошибок, сохранение ключей в открытом виде, DLL Injection, Memory Injection, чтение памяти игр, обход античитов.

------------------------------------------------------------------------

# 26. Обязательные отчёты при крупных изменениях

При изменении архитектуры, структуры профилей, БД, OCR-подсистемы, Overlay, системы переводчиков – сначала описать проблему, решение, преимущества, недостатки, влияние на совместимость.

------------------------------------------------------------------------

# 27. Критерий успешной работы агента

Создание небольших законченных изменений, сохранение существующей функциональности, соблюдение архитектуры, следование Roadmap, обновление документации.

------------------------------------------------------------------------

# 28. Финальное правило

Выбирать решение: наиболее простое, соответствующее ТЗ и архитектуре, с минимальным объёмом изменений, сохраняющее обратную совместимость.
