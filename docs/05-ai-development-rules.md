# AI Development Rules

## Правила работы ИИ-агента

Проект: Система экранного OCR-перевода игровых субтитров и текста для Windows 11

Версия документа: 2.0

------------------------------------------------------------------------

# 1. Назначение

Эти правила помогают агенту поставлять небольшие проверяемые изменения, сохранять архитектурные границы и не превращать исторический roadmap в искусственную блокировку разработки.

------------------------------------------------------------------------

# 2. Приоритет источников

1. Конституция проекта: жёсткие инварианты.
2. Явное решение владельца и принятый ADR в пределах его scope.
3. Техническое задание: продуктовые требования.
4. Архитектура: текущее устройство реализации.
5. GitHub Issues и их зависимости: текущий порядок поставки.
6. Roadmap и Sprint Plan: исторический контекст и покрытие возможностей.
7. Технические риски, Definition of Done и этот документ.

При конфликте источников агент останавливается только для Hard Stop или неясного Decision Record. В остальных случаях он фиксирует расхождение и предлагает минимальное согласование документации.

------------------------------------------------------------------------

## Текущий OCR baseline (ADR-030)

Перед изменением OCR, live pipeline, packaging или release agent читает ADR-030 и `docs/agents/ocr-overlay-work-status.md`. Нормальный маршрут — GPU Paddle detector → bounded grouping → существующий Tesseract crop recognition → configured translator → per-region overlay. Python допустим только как зафиксированный packaged detector worker; UI, профили, orchestration, provider selection и overlay остаются в .NET.

Legacy full-page OCR/grouping не выбирается автоматически и доступен только через явный diagnostic/compatibility option. Недоступность detector/runtime должна оставлять контролируемое degraded-состояние: агент не добавляет full-frame retry, WebAuto/cache/provider fallback и не меняет provider default без нового решения владельца. Windows OCR и Tesseract остаются обязательными продуктными возможностями.

Для внешней публикации агент не добавляет в Git screenshots, game/manga OCR-тексты, calibration evidence, release candidates, модели или Tesseract data, если владелец отдельно не одобрил именно эти материалы.

------------------------------------------------------------------------

# 3. Классификация изменений

Перед правкой агент сверяет `docs/governance/change-approval-required.md`.

- **Hard Stop**: вмешательство в процессы или память игры, обход античита, хранение секретов вне Credential Manager, разрушительное изменение профилей или слоёв. Такое изменение возможно только после явного решения владельца.
- **Decision Record**: замена платформы или публичного контракта, изменение поведения по умолчанию, политика TTL и обхода кэша, совместимость профилей, новая продуктовая политика или ADR. Нужны обоснование и явное решение владельца.
- **Normal Delivery**: исправление дефекта, тест, документация, совместимое расширение, настройка алгоритма в принятом ADR, обновление пакета без смены архитектурной роли. Агент выполняет такую работу самостоятельно.

Принятый ADR является разрешением реализовать описанный в нём scope. Новое решение нужно, только если работа выходит за этот scope.

------------------------------------------------------------------------

# 4. Подготовка к работе

Перед изменением агент читает обязательные документы и локальные `AGENTS.md`, определяет целевую GitHub Issue или прямой запрос владельца, её зависимости, затронутые модули и применимые Quality Gates.

Независимые исправления, тесты, документация и совместимые улучшения можно выполнять параллельно. Номер исторического спринта не является самостоятельным запретом на такую работу.

------------------------------------------------------------------------

# 5. Архитектурные границы

Используются C#, WPF, MVVM и Clean Architecture. `Domain` не зависит от UI, Infrastructure и внешних фреймворков. Прямая зависимость UI от Infrastructure запрещена.

Интерфейс создаётся на границе внешней системы, побочного эффекта или между слоями. Не следует добавлять интерфейс для внутреннего класса только ради формального DI. Overlay остаётся отдельной ответственностью, но не обязан существовать как отдельная техническая сборка.

------------------------------------------------------------------------

# 6. Безопасность и профили

Запрещены DLL Injection, чтение или изменение памяти игр, обход античитов и другие процессные вмешательства. Захват выполняется только через поддерживаемые Windows screen-capture API.

Секреты хранятся только в Windows Credential Manager и никогда не попадают в JSON, SQLite, логи, отладочные файлы или сообщения пользователю. Изменение существующего формата профиля должно сохранять чтение старых профилей или включать явную миграцию; разрушительная миграция требует Hard Stop.

------------------------------------------------------------------------

# 7. OCR и переводчики

Каждый экранный OCR-движок реализует `IOcrEngine`; Windows OCR и Tesseract сохраняются как обязательные возможности. Для вертикального текста Tesseract используется по умолчанию. Новый экранный движок допускается после бенчмарка на утверждённых скриншотах и ADR, не вместо существующих движков.

Каждый официальный переводчик реализует `ITranslatorProvider`. Смена набора обязательных провайдеров или их автоматическая политика требует решения. `WebAuto` остаётся диагностическим экспериментом и не является тихим production fallback.

------------------------------------------------------------------------

# 8. Overlay, группы и координаты

Сырые OCR-блоки служат диагностикой и источником маски; pipeline может формировать семантические группы для перевода. Маска и текст перевода имеют разные геометрии согласно принятому ADR.

Координаты поддерживают абсолютный и относительный режимы. Многозонность должна сохраняться: локальное изменение не должно ломать независимую работу других зон. Проверка нескольких зон нужна, когда изменение может на неё повлиять.

------------------------------------------------------------------------

# 9. Кэш и асинхронность

Перед штатным переводом pipeline проверяет кэш с TTL 30 дней. Исправление кэша и его тестов является обычной поставкой; изменение TTL, default bypass или политики ключа требует решения и измерения. Обход кэша допустим только как явная, не-default диагностическая операция.

OCR, захват, сеть и перевод выполняются асинхронно вне UI-потока. Конкретное число потоков определяется реализацией и профилированием, а не фиксированным правилом.

------------------------------------------------------------------------

# 10. Качество и производительность

Используются Quality Gates из `docs/07-definition-of-done-quality-gates.md` по влиянию изменения. Сборка, новые предупреждения, архитектурные границы и секреты проверяются всегда; UI, OCR, overlay, кэш, профили, производительность и интеграции проверяются, если затронуты.

Перед оптимизацией измеряется затронутый путь. Цели OCR не более 200 мс, среднего CPU не более 25% и памяти не более 500 МБ являются ориентирами продукта; отклонение фиксируется измерением и Issue, а не блокирует исследование или безопасный багфикс.

------------------------------------------------------------------------

# 11. Тесты, ошибки и документация

Изменённое поведение имеет тесты, соразмерные риску: значимые успешные, ошибочные и граничные сценарии. Тестовые часы и внешние зависимости должны быть детерминированными настолько, насколько позволяет существующая архитектура.

Пустой `catch` запрещён. Ошибки и предупреждения логируются без секретов. Пользователь получает короткое восстановимое состояние для захвата, OCR, языкового пакета, переводчика или overlay, а технические детали остаются в журнале.

Документация обновляется, когда меняются публичный контракт, настройка, архитектурное решение или пользовательское поведение. Ссылки на артефакты следуют `docs/evidence-artifacts.md`.

------------------------------------------------------------------------

# 12. Масштаб изменения

Предпочтителен минимальный понятный change set. Массовый рефакторинг, смена слоёв или замена платформы требуют ADR или явного решения. Обычный багфикс не нужно искусственно расширять до рефакторинга.

------------------------------------------------------------------------

# 13. Завершение задачи

В итоговом сообщении агент указывает изменённые файлы, результат, выполненные проверки, известные риски и оставшиеся зависимости. Для значимой задачи он обновляет GitHub Issue и проверяет опубликованный комментарий. Процент готовности указывается для вехи или релиза, а не как формальный отчёт после каждой маленькой правки.

------------------------------------------------------------------------

# 14. Финальное правило

Выбирать самое простое решение, которое соответствует инвариантам, принятому ADR и затронутым продуктовым требованиям, сохраняет совместимость и даёт проверяемый результат.
