# PROJECT CONSTITUTION v1.0

## Проект

Game Translator

Система распознавания и перевода текста в компьютерных играх в режиме реального времени для Windows 11.

Статус документа: ОБЯЗАТЕЛЬНЫЙ К ИСПОЛНЕНИЮ

Версия: 1.0

Нарушение любого пункта Конституции требует явного согласования владельца проекта.

---

# 3. ЦЕЛЬ ПРОЕКТА

Создать приложение Windows 11, которое:

* захватывает экран;
* распознаёт текст;
* переводит текст;
* скрывает оригинальный текст;
* отображает перевод поверх игры;
* работает в режиме реального времени;
* не взаимодействует с памятью игры.

# 9. ПРАВИЛО OCR

Минимум два OCR-движка:

1. Windows OCR
2. Tesseract OCR

Запрещено:

* удалять один из движков;
* делать продукт зависимым только от одного OCR.

Для вертикального текста:

Tesseract является обязательным и проверенным default. Альтернативный OCR для вертикального текста допускается только после benchmark на screen-capture fixtures, ADR и явного решения владельца; Windows OCR и Tesseract при этом остаются поддерживаемыми.

# 18. ПРАВИЛО ПРОИЗВОДИТЕЛЬНОСТИ

Цели MVP:

OCR <= 200 мс

Overlay <= 16 мс

CPU <= 25% среднее

CPU <= 50% пик

RAM <= 500 МБ

Для изменения OCR, capture, translation, overlay или горячего пути производительности требуется baseline и измерение результата. Небольшой безопасный рефакторинг не требует отдельной оптимизационной процедуры.

ADR-023 задаёт отдельную продуктовую семантику для текста, который остаётся видимым 3–4 секунды: после стабилизации независимые текстовые регионы доставляются в overlay прогрессивно и не ждут обработки остальных регионов кадра. Базовая конфигурация benchmark для GPU candidate detector — CPU от шести ядер и NVIDIA RTX 3060 с 8 ГБ VRAM; точные end-to-end P50/P95 пороги принимаются только после измерений на этой конфигурации.

Предпочтительны минимальные и обратимо проверяемые изменения. Массовое переписывание, смена архитектуры или технологии требуют ADR; исправление, расширение и рефакторинг внутри принятого ADR выполняются обычным способом через issue, тесты и review.

# 20. ПРАВИЛО ROADMAP

Roadmap задаёт рекомендуемый порядок, а фактические зависимости ведутся в GitHub Issues. Работы могут идти параллельно, если их технические и продуктовые зависимости выполнены. Незавершённый риск должен быть либо закрыт, либо явно отложен с владельцем; он не блокирует независимую подготовительную работу автоматически.

---

# 21. ПРАВИЛО QUALITY GATES

Для каждой задачи выбираются применимые Quality Gates по её влиянию. Базовые gates сборки, тестов, архитектуры и секретов обязательны всегда; неприменимые gates отмечаются с кратким обоснованием. Полный набор релевантных gates обязателен для спринта и release-кандидата.
